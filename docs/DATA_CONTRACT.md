# Data Contract — `public/data/*.json`

What Phase 2 (React) can rely on. Every file is generated by
`scripts/generate_mock_data.py` and verified by `scripts/validate_mock_data.py`.

All 14 files total **3.5 MB** uncompressed (roughly 700 KB gzipped, which is what Vercel
serves). Largest is `enrollment_by_course.json` at 1,007 KB.

Field names are copied from the original Shiny dashboard wherever the original had an
equivalent, so a reader who knows that codebase can follow this one. Where a name is new,
it is called out.

---

## Conventions

**Course codes** — `"DEPT NNNN"`, e.g. `"CS 2500"`. Single space. Used as the primary key
everywhere; every cross-file reference resolves (validated).

**Term codes** — 6-character strings, academic-year Banner coding:
`{academic_year}{season_code}` with `Fall=10, Spring=20, Summer 1=30, Summer 2=40,
Summer Full=50`. Fall 2022 → `"202310"`. Codes sort chronologically as strings.
Season sub-codes are copied from the original's `utils/program_utils._TERM_CODE_SEASON`;
the academic-year convention is confirmed by `config.FALL_2023_TERM = 202410` and by
`model_data/course_term_enrollment.csv`. See `ORIGINAL_APP_MAP.md §8.1` for the
inconsistency in the original this resolves.

**Levels** — `1`–`4`, the first digit of the catalog number. The original derived this the
same way (`get_course_level`).

**Rounding** — probabilities and rates to 4dp, currency-like counts to integers,
betweenness to 8dp.

### Degrees are whole-graph — recompute them for filtered views

`in_degree`, `out_degree`, `betweenness`, `cascade_impact` and `prereq_chain_depth` are
computed over the **entire** 820-course graph. The original's Graph Statistics card is
computed over whatever is *currently visible*, so under any active filter these values are
wrong for it:

| Graph Statistics row | how to derive under a filter |
|---|---|
| Total Courses | count of visible nodes |
| Total Dependencies | count of edges with both endpoints visible |
| Avg Prerequisites | Σ in-degree **within the visible subgraph** / n |
| Max Prerequisites | max in-degree within the visible subgraph |
| Key Courses | top 5 by out-degree **within the visible subgraph**, zero excluded |
| Total Courses By Level | count of visible nodes per `level` |

Filter `prerequisites.json → edges` to the visible node set and count — it is a single pass
over 1,145 edges. For the program-filtered case specifically,
`program_structures.json` already carries the correct subgraph values
(`total_courses`, `num_connections`, `avg_prereqs`, `max_prereqs`), so use those rather than
recomputing.

The whole-graph values remain the right input for the *unfiltered* view, for
`bottleneck_score` (the RF was trained on whole-graph features), and for sizing nodes.

### `elective_context`

Replicates `load_data._process_version` and `_build_choice_label`. 415 of 820 courses carry
it. `choice_label` strings are generated by the original's exact rules:

| section | label |
|---|---|
| `advisor` | `Advisor-approved — select with your advisor from "{name}"` |
| `selection_count` set | `Pick {n} of {total} courses from "{name}"` |
| `credits_required` set | `Earn {n} credits from "{name}"` |
| `credits_total` set | `Pick courses totalling {n} credits from "{name}"` |
| otherwise | `Choose from "{name}"` |

Range-derived entries get `elective_type: "range"`, `is_range: true` and a
`range_description` like `"CS 4000–4999"`. The original's hover renders ranges as
**Elective (Open Range)** with Section and Range lines, and concrete choices as the section
name followed by the choice label.

### Layout coordinates

Two precomputed coordinate sets ship per course. **Render `x`/`y`.**

`x`/`y` — **layered DAG layout, the default.** Tier is still the course level, so vertical
distance still reads as prerequisite depth, but the ordering *within* each tier is
crossing-minimised (barycentre heuristic, 8 alternating sweeps) instead of alphabetical.
Spacing is adaptive.

`x_hier`/`y_hier` — the original's `create_hierarchical_layout` verbatim: grouped by level,
**sorted alphabetically** within level, `x_spacing=150`, `y_spacing=100`, levels stacked
downward. Kept so the two can be compared side by side.

Measured on the generated catalog (also in `prerequisites.json → layout`):

| | original (alphabetical, 150px) | shipped (layered DAG) |
|---|---|---|
| Edge crossings | 10,621 | **4,712** (−55.6%) |
| Total width | 38,250 px | **11,427 px** (−70.1%) |
| Mean edge horizontal span | 4,913 px | **1,241 px** (−74.7%) |
| …as a fraction of layout width | 0.128 | **0.109** (−15.4%) |
| Edges within 100 px of vertical | 22 | **152** (7×) |
| x spacing | 150 px | 47 px |

Three independent mechanisms produce those numbers, and it is worth knowing which does
what:

1. **Barycentre ordering** cuts crossings by 55.6%. It does not narrow anything — a tier's
   node count is fixed — and on its own it barely shortens edges.
2. **Adaptive spacing** cuts width by 70%. Appropriate because node radius already shrinks
   with graph size in the original (`max(15, min(35, 500/n))` → 15 px here), so 150 px
   gaps between 15 px dots are mostly empty canvas.
3. **Priority coordinate assignment** (Sugiyama step 4) is what actually shortens edges,
   sliding each node toward the mean x of its neighbours within bounds that preserve the
   ordering. Minimum separation is set below the initial spacing on purpose: with the two
   equal, every node's bounds collapse onto its current position and nothing moves.

Normalised edge length still only improves 15.4%, and that is close to the ceiling for a
layered layout at this density — with 256 nodes in a tier and most of them carrying one or
two edges, no single 1D ordering can put every linked pair adjacent. The near-vertical edge
count is the better indicator of the practical gain: 152 chains now read as chains against
22 before.

Force-directed is the toggle, computed client-side from `prerequisites.json → edges`; it
needs no precomputed coordinates. It discards the level→vertical mapping, so offer it for
exploring cluster structure, not for reading depth.

Even at 11,427 px the unfiltered graph is wide. The original handled this by prompting the
user to filter first (`server.py:49-54` shows *"N courses detected. Select a program or
department for clearer visualization!"* above 100 courses) — worth reproducing. A
program-filtered view is 3–33 courses and reads comfortably.

**`prereq_logic` matters for rendering prerequisite groups.** `SINGLE`/`OR` → one
OR-group; `AND` → one group per prerequisite; `COMPLEX` → split `prerequisite_text` on
`;` into AND-groups, `or` within each. Port `parse_prerequisite_groups` from
`generate_mock_data.py` if the UI needs to show "one of / all of".

## `program_structures.json` — 78 KB

`{"required_mode": {...}, "all_mode": {...}, "metric_definitions": {...}}`, keyed by
program code. Drives the `view_all_courses` toggle without recomputation.

Every metric replicates `graphs.calculate_program_metrics`, computed on the **program
subgraph**: `total_courses`, `num_connections`, `avg_prereqs`, `max_prereqs`, `density`,
`max_depth`, `cross_program_share`, `avg_unlocks`, `foundational_ratio`, `level_ratios`,
`modularity_proxy`, `bottleneck_courses` (top 3), plus `degree_type` and `total_credits`.

Two fields the blueprint asks for that the original did not compute, added alongside:
`cross_dept_pct`, `gateway_count`.

**`density` keeps the original's convention** — directed edge count over undirected
maximum pairs `n(n-1)/2` — so values can exceed 0.5. Preserved for parity and documented
in `metric_definitions`. Sort program cards by `max_depth` descending to match the
original.

**Join `courses` to `scenarios[pct].deltas` by course code** to build a table row. Only
the four `delta_keys` change with growth; repeating the rest five times cost ~1 MB.

Formulas (from `demand_aggregator.calculate_demand_forecast`, reproduced exactly):
```
weighted_demand  = Σ rank_r_count * rank_weight_r * (1 + growth)
current_capacity = max_enrollment_capacity * sections_per_semester
shortage         = max(0, weighted_demand - current_capacity)
sections_needed  = ceil(shortage / 40)
priority_score   = shortage*0.4 + ml_risk*100*0.3 + weighted_demand*0.3
```
UI thresholds from `admin_demand_renderer`: ML risk badge `>0.8` HIGH danger, `>0.6`
MODERATE warning, else LOW success. Shortage text `>40` danger-bold, `>20` warning-bold,
else muted; render `0` as `—`. `critical_courses` = `ml_risk > 0.7 AND weighted_demand >
30`, top 10 by `priority_score`.

`enrollment_forecast_model` is the second, separate demand path — the RandomForest
enrollment forecaster the original trained in R and never wired into the dashboard.
Carries `models` (Naive / Linear Regression / Random Forest with `test_mae` and
`improvement_pct`), `features`, `feature_importance`, and up to 400 `predictions`.

## Filter behaviour to reproduce

From `ORIGINAL_APP_MAP.md §2`, the parts that constrain the data:

1. **Department and program are mutually exclusive** — committing one resets the other.
2. **Terms cascade both ways** — terms restrict the program and department lists;
   a program restricts the term list to its active terms across *all* versions.
3. **Selecting a program with no term chosen auto-selects its most recent term.**
4. **Concentration filter appears only when the selected program has concentrations** —
   check `index[].has_concentrations`.
5. **Program version resolution** — pick the version whose `effective_period` overlaps a
   selected term, else the most recent by `end_date`.
6. **`view_all_courses` is Program-Metrics-only** and switches
   `program_structures.required_mode` ⇄ `all_mode`.
7. **Cascade grey-out (Graph View)** — removing a course greys it `#374151` and every
   downstream dependent `#d1d5db`, following prerequisite successors *and* corequisite
   out-edges. Absent from the blueprint; the most distinctive interaction in the original.
